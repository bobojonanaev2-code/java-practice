проекты не зависят друг от друга.

## Открытие и запуск в Visual Studio Community

1. В **Visual Studio Installer → Изменить** установите рабочую нагрузку
   **«Разработка классических приложений на C++»** (Desktop development with C++),
   включая MSVC для x64/x86 и Windows SDK. Одной установки IDE недостаточно.
2. Откройте `CppPractice.sln` через **Файл → Открыть → Проект/решение**.
3. Выберите **Debug | x64**, затем **Сборка → Собрать решение** (`Ctrl+Shift+B`).
4. В обозревателе решений нажмите правой кнопкой на `task-16-8` или `task-16-9`
   и выберите **«Назначить запускаемым проектом»** (Set as Startup Project).
5. Запустите выбранный проект с помощью `Ctrl+F5`. Без аргументов открывается меню.
   Для второго задания смените запускаемый проект.

В проектах включены `/std:c++17`, `/utf-8`, предупреждения `/W4` и стандартные
исключения C++. Используется стандартный набор инструментов установленной
Visual Studio (`DefaultPlatformToolset`), Windows SDK выбирается из установленных
версий 10.x. Решение в формате `.sln` предназначено для Visual Studio 2022 и новее.
В Windows программы переключают консоль на UTF-8. В числах используйте точку,
а в коэффициентах многочленов — целое число или дробь вида `-3/5`.

## Автоматические проверки и демонстрация

Каждый проект поддерживает `--test` (проверки) и `--demo` (контрольный пример).
В Visual Studio аргумент задаётся в **Свойства проекта → Свойства конфигурации →
Отладка → Аргументы команды**. Перед возвращением к меню очистите аргументы.
Проверки работают и в Release: они используют исключения, а не отключаемый `assert`.

Из **Developer PowerShell for Visual Studio**, в корне репозитория:

```powershell
msbuild .\CppPractice.sln /m /p:Configuration=Debug /p:Platform=x64
if ($LASTEXITCODE -ne 0) { throw 'Ошибка сборки' }
& .\.build\x64\Debug\task-16-8\task-16-8.exe --test
if ($LASTEXITCODE -ne 0) { throw 'Ошибка проверок 16.8' }
& .\.build\x64\Debug\task-16-9\task-16-9.exe --test
if ($LASTEXITCODE -ne 0) { throw 'Ошибка проверок 16.9' }
```

Повторите команды для `Release`, заменив `Debug` в параметре и путях.
При успехе ожидается сообщение «Все проверки задания … пройдены» и код возврата 0;
при ошибке — описание проверки и код 1. Это **ожидаемое поведение**, а не отчёт
о состоявшемся запуске.

Для сборки и комплексной проверки, включая меню, ошибочный ввод, сохранение
объектов после ошибки и завершение ввода, запустите из PowerShell:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\Verify.ps1 -Configuration Debug
powershell -NoProfile -ExecutionPolicy Bypass -File .\Verify.ps1 -Configuration Release
```

Скрипт ищет MSBuild через `PATH` или установленный Visual Studio Installer.
При отсутствии C++ компонентов он останавливается с сообщением; тесты
не отмечаются как пройденные. Политика `Bypass` действует только в запущенном
процессе PowerShell и не меняет настройки системы.

Если доступен GCC, из корня репозитория можно проверить переносимый код:

```sh
mkdir -p .build/gcc
g++ -std=c++17 -Wall -Wextra -Wpedantic task-16-8/*.cpp -o .build/gcc/task-16-8
g++ -std=c++17 -Wall -Wextra -Wpedantic task-16-9/*.cpp -o .build/gcc/task-16-9
.build/gcc/task-16-8 --test
.build/gcc/task-16-9 --test
```

## Статус проверки в среде подготовки

каталог `VC` и C++ targets отсутствуют. `cl`, `g++` и `clang++` в Windows не найдены;

отсутствует `Microsoft.Cpp.Default.props` из компонентов C++.
Поэтому **сборка и выполнение C++
не проверены**, автоматические проверки подготовлены, но не запущены.
